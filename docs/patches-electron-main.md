| `src-electron/main.js` | `SQLite`/`WebApi` .NET object `Init()` calls removed entirely. IPC handlers: `vrcx-connect-server` (logs into a remote server, opens `/api/agent`, answers forwarded calls via the real `interopApi.callMethod`), `vrcx-rpc` (relays `database`/`config`/`webapi`), `vrcx-totp-setup`/`vrcx-totp-confirm`, and the multi-server set `vrcx-list-servers`/`vrcx-switch-server`/`vrcx-remove-server`/`vrcx-set-default-server`/`vrcx-get-server-status` (`VRCX_Servers` storage, reachability tracking, `restartApp()` extracted so both `app:restart` and the switch handler share it — `vrcx-get-stored-server-url` was removed once `vrcx-list-servers` made it a strict subset). A startup gate probes the stored session before loading the real app vs. `client-desktop/setup.html`. Also fixes a genuine pre-existing upstream bug (predates this fork, `74bae434`): `--x11` only skipped the auto-relaunch decision without telling Chromium to actually use X11, so on Wayland+Vulkan the window never became visible — now appends `ozone-platform=x11` to `app.commandLine`. Found live (2026-08-17): connecting to a self-signed-but-OS-trusted headless server (e.g. a homelab `step-ca` cert already in the Windows trust store) failed every RPC call with a bare `fetch failed` — this process's `fetch`/`ws` calls run through plain Node's TLS stack, which trusts only its own bundled Mozilla CA bundle, never the OS certificate store, regardless of what the OS or a browser trusts. `vrcx-import-ca-cert`/`vrcx-remove-ca-cert`/`vrcx-get-ca-cert-status` let a user import a CA cert from the connection UI, written to `<userData>/custom-ca.pem`; a self-relaunch gate at the top of the file sets `NODE_EXTRA_CA_CERTS` to that path and restarts once whenever the file exists but the running process wasn't started with it, since Node only reads that env var at process bootstrap, never at runtime. Also found live the same day: `vrcx-stream-connect`/`vrcx-stream-close` open the real `/api/stream` connection here (with the `Authorization: Bearer` header the renderer can't attach itself) and forward every frame to `client-desktop/shims/pipeline-relay.js`'s relayed `WebSocket` object — see the seam table's Pipeline WS row for why this replaced a direct renderer→VRChat connection. Found live (2026-08-23): every `fetchJson` failure surfaced as a bare, unactionable `"fetch failed"` (Node's `fetch` collapses refused connections, DNS failures, timeouts, and TLS errors into that one message, with the real reason nested in `err.cause`) — `describeFetchError()` unwraps it once at the `fetchJson` choke point into text a user can actually act on (e.g. "is a VRCX server actually running at that address and port?"), reaching every caller for free. Also found live the same day, on real hardware rather than a sandbox (two earlier "fixes" both silently tested a stale cached AppImage extraction and never actually ran): `restartApp()`/`before-quit`/the ozone self-relaunch could leave the old process and tray icon stuck forever with no new window ever appearing, because `app.exit()`'s native shutdown path can itself hang on this Linux session (DBus/tray teardown) — `scheduleForceExitFallback()` spawns a detached `sh -c 'sleep 3; kill -9 <pid>'` watchdog, scheduled as the *first* action in each of those three call sites (a `setTimeout`-based fallback tried first is provably useless: it can never run on a thread that's blocked in the exact native call it's meant to route around), immune to that same hang since `SIGKILL` is delivered by the kernel regardless of what the target thread is doing. Also renamed every user-facing string in this file (`mainWindow`'s `title`, pinned against the upstream page overwriting it via `page-title-updated`; the tray tooltip/quit-menu label; every `dialog.showErrorBox`/`showMessageBoxSync`) from plain `VRCX` to `VRCX Headless Desktop` — `client-web/**`'s and `client-desktop/setup.{html,js}`'s own title tags/headings got the matching `VRCX Headless Web`/`VRCX Headless Desktop` treatment, fork-owned files needing no separate log entry here — so a running instance of this fork is never mistaken for the real desktop app at a glance. Also found live the same day: `installVRCX()`/`updateDesktopFile()` hardcoded plain `VRCX.AppImage`/`VRCX.desktop` throughout (upstream's own convention, otherwise unmodified) — the exact filenames the real desktop app installs to, so a machine with both installed would have each one silently overwrite the other's copy in `~/Applications` and launcher entry in `~/.local/share/applications` depending on launch order, and `updateDesktopFile()`'s own "no existing file" branch also read the wrong bundled filename to begin with (`electron-builder.config.js`'s `desktopName` actually bundles `VRCX-Headless.desktop`, never `VRCX.desktop`, so that branch always failed silently on a genuinely fresh install). Both the installed AppImage and desktop-entry filenames are now `VRCX-Headless.{AppImage,desktop}` throughout, matching what's actually bundled and never colliding with the real app's own files; `electron-builder.config.js`'s `linux.desktop.entry.Name` updated to `VRCX Headless Desktop` to match. Found live (2026-08-23, Windows): `getVersion()` (feeding `AppApi.GetVersion()`, and so the Settings page's "Version" line) hardcoded a hardcoded `VRCX (Linux)` prefix regardless of actual host OS — a leftover from upstream only ever building this Electron client for Linux (§1's "Desktop client OS support" table) — misleading once this fork's Electron build genuinely runs on Windows too; now `VRCX Headless`. Also switched the number after that prefix from the raw upstream `Version` file (`2026.07.18`) to `app.getVersion()` — this fork's own release version, i.e. `package.json`'s `version` field as patched at build time by `build-scripts/patch-package-version.js` (same `<vrcx-date-no-dots>.<fork-build>.0` scheme as the Docker tag, CLAUDE.md's "Server/Docker versioning") — so the Settings page shows which *fork release* is installed, not just which upstream date it's based on; the raw upstream string is still shown separately (`src/stores/vrcxUpdater.js`'s new `upstreamVersion`, "Based on VRCX version" in Settings). Found live (2026-08-24, Windows, via the new fork-updater's restart-after-install path — §9): `scheduleForceExitFallback()` was only ever externally gated to `process.platform === 'linux'` at *two* of its three call sites (`restartApp()`'s Linux branch, `tryRelaunchWithArgs`'s own early return) — the third, the global `app.on('before-quit', ...)` handler, calls it unconditionally on every platform. Since that handler fires on *any* `app.quit()`, including `restartApp()`'s own Windows branch, a plain Windows restart threw an uncaught main-process exception ("spawn sh ENOENT" — the watchdog's whole mechanism is a Linux-only DBus/tray-teardown workaround that shells out to `sh`, which doesn't exist on Windows) right after a successful update download. Moved the guard inside `scheduleForceExitFallback()` itself instead of patching the third call site alone, so every caller — present or future — is safe by construction rather than by remembering to check the platform first. Also (2026-08-24, same day): new `checkAndInstallForkUpdate()`, called from `app.whenReady()` *before* `createWindow()` — the fork-updater's real entry point now, moved here from a post-auth renderer trigger for the reason §9's own write-up covers in full; talks to the server's new unauthenticated `GET /api/update-info` and calls `AppApiElectron.DownloadUpdate` directly, no window/IPC needed this early. Later the same day: the installer-relaunch fix and `showSplash()`/`updateSplashStatus()`/`closeSplash()`, both covered in full in §9. **(2026-08-28)** `checkAndInstallForkUpdateInner()` extended to Linux (asset-suffix branch, `Update.Init(appImagePath)` wiring, a from-scratch Linux relaunch path), plus the two live-found `app.exit()`/`app.relaunch()` bugs fixed alongside it, and — found from the user's own run rather than the sandboxed test — a `postUpdate` flag (`--post-update`) suppressing `installVRCX()`'s "install to `~/Applications`?" dialog for a post-update relaunch, and the relaunch itself carrying `tryRelaunchWithArgs()`'s own flags to avoid a second, stacked self-relaunch, and — hardening hash verification to fail closed rather than fail open — a new `parseSha256Digest()` helper the download step now calls instead of a bare `?.startsWith('sha256:')` check. **(2026-08-28, later)** The `customCaCertPath` self-relaunch above (2026-08-17's own entry) turned out to never actually work on this Electron/Linux combination: its bare `app.relaunch()` doesn't carry the just-mutated `process.env.NODE_EXTRA_CA_CERTS` to the relaunched child — that call apparently uses the process's environment from when *it* was launched, not later in-JS `process.env` writes — so a machine with a `custom-ca.pem` on disk hit the exact same "cert exists, var missing" check on every relaunch, forever: a fast, silent, resource-churning loop with no window ever created, reported as "the app appears on the taskbar with no window then closes." Fixed by passing `env: process.env` explicitly. Verified live: without the fix, nothing was ever logged anywhere (no `fork-update.log`, no `.NET` NLog output) no matter how long it ran; with it, exactly one (the pre-existing, unrelated Wayland/ozone) relaunch happens and the app proceeds normally. `restartApp()`'s own two `app.relaunch()` calls below didn't need the same fix — they only ever run once the process's actual environment already has whatever it needs, not right after a same-tick `process.env` mutation; `tryRelaunchWithArgs()`'s relaunch uses a plain `child_process.spawn()`, which does inherit `process.env` normally, unlike Electron's own `app.relaunch()`. **(2026-08-28, later still)** `updateDesktopFile()`'s `Exec=` value hardened twice more, both found live diagnosing a real launch failure on a real machine (full write-up: `client-desktop/README.md`'s new "Troubleshooting" section, user-facing since this affects any installed AppImage, not just a dev/build concern): (1) it now always appends ` --ozone-platform-hint=auto` (unless `x11`) — a plain double-click launch, going through this `Exec=` line with no argv of its own, crashed outright (a real SIGTRAP/coredump) on a Wayland+Vulkan session, and `tryRelaunchWithArgs()` above can't reliably win that race since Chromium's own ozone-platform selection happens natively, early enough to sometimes beat the JS relaunch decision — reproduced live as genuinely intermittent, same binary and `Exec=` line, sometimes crashing and sometimes not. The only fully reliable fix is for the very first exec to already carry the flag. (2) When `customCaCertPath` exists, `Exec=` now also gets an `env NODE_EXTRA_CA_CERTS=<path> ` prefix — found live on the same machine, after fixing (1): the `env: process.env` fix to that self-relaunch (this entry's own first half) worked reliably in an unpackaged dev run but *consistently failed* in the packaged AppImage build on real hardware — no window, nothing logged anywhere, every time — despite FUSE mounting, `AppRun`'s own script, and sandbox/namespace probing all individually checking out fine in isolation. The packaged-vs-dev discrepancy itself was never root-caused. Baking the env var into `Exec=` directly sidesteps the unreliable relaunch entirely for a desktop-icon launch, is a standard supported `Exec=` pattern, and self-heals on the very next launch after any `vrcx-import-ca-cert`/`vrcx-remove-ca-cert` call (since this function runs on every startup); the self-relaunch itself stays as the fallback for a launch that doesn't go through this `Exec=` line at all.
